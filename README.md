# Code review

`/code-review` starts a structured review of a GitHub pull request in a **background subagent**. The command returns immediately; the main agent delegates the review, the child prepares the context with `prepare_code_review` and reviews in its own context, and the main session only relays the report. It is designed for the Web client, and works anywhere slash commands are available. On the Web client, the plugin's page in **Plugins** carries a settings card for the report language, finding limit, and context budgets.

## Requirements

- The `gh` CLI installed and signed in (`gh auth login`). The plugin runs `gh` itself, so `GH_TOKEN` in the environment is not forwarded; sign in through `gh` instead.
- A GitHub-hosted pull request. GitLab and other code hosts are not supported.
- A session with a working directory. It is used for the review context directory.
- A preset with the `subagent` delegation tool (the standard preset provides it). Without it, the command reports that background review requires delegation.
- Node.js 22.18 or newer for development: tsdown bundles the sources, and the tests run as TypeScript under Node's type stripping. The plugin itself runs in the Harness's Node process.

## Install

Open **Plugins** and add the **package root** with **Add plugin** — the directory containing `package.json` and `cordis.patch.yml`. For this checkout that is the repository root, **not** `lib/`: the dialog reads `<path>/package.json` and then the bundle patch, so `lib/` alone is not a valid plugin package. Enabling the bundle inserts one Host row, `code-review`, and loads the package's small built Client bundle for the settings card.

The Harness loads the compiled entry `lib/index.js`. `lib/` is generated by `npm run build` and is not committed, so after cloning run `npm install && npm run build` once, and rebuild after editing `src/`, before adding the directory or reloading.

### Debian package

`make deb` builds and verifies an architecture-independent package:

```sh
make deb
sudo apt install ./dist/dsh-code-review_*_all.deb
```

The package depends on `deepseek-harness (>= 0.2.2~rc.3)` and recommends `gh` and `git`. It installs the plugin package root under `/usr/lib/dsh/plugins/code-review` (including its pinned `schemastery` schema dependency) and notes under `/usr/share/doc/dsh-code-review`; it never edits a user profile and installs no service. Enable it per user, then let the profile reload:

```sh
dsh plugin --profile web add /usr/lib/dsh/plugins/code-review
systemctl --user restart dsh-web     # only if the profile does not reload live
```

The same directory works in **Plugins → Add plugin**. An upgrade replaces the directory in place, so the profile link stays valid; restart the Host to load the new code. Remove the bundle (`dsh plugin --profile web remove @local/dsh-code-review`) before `apt remove dsh-code-review`.

`release.conf` holds the package identity, the apt revision, the `deepseek-harness` floor, and the install path; `make print-config` prints the resolved values. `make DEB_REVISION=alex1 deb` rebuilds with a different revision. The payload is `Architecture: all` because the plugin is pure JavaScript.

### Continuous integration

`.github/workflows/ci.yml` runs on pull requests into `main`: it installs the locked dependencies, builds `lib/`, typechecks, and runs the unit tests against that output.

`.github/workflows/build-deb.yml` runs on `v<version>` tags that match `package.json`, and on manual dispatch: it builds and verifies the deb, then publishes the `.deb` and its `.sha256` to a GitHub Release.

## Use

```text
/code-review                        review the open pull request of the current branch
/code-review 123                    review PR #123 in the repository of the session directory
/code-review owner/repo#123         review #123 in another repository
/code-review https://github.com/owner/repo/pull/123
```

The command validates the selector and submits one delegation turn, then returns. The main agent calls the `subagent` tool with a self-contained review task; the child calls `prepare_code_review`, which resolves the pull request, fetches its metadata, the patch of every changed file, and the complete text of those files at the head commit, and writes that material under `.dsh/code-review/<owner>-<repo>-<pr>-<head>/`. The child reads the returned `index.md`, loads the `dsh-code-review` skill, and returns the report as its final answer. The main agent relays that report when the completion notice arrives.

The split is deliberate: the command does no network work, so the composer is released as soon as you submit; the review runs in a separate context, so the main session is not filled with the diff, file reads, or verification steps. The main session only sees the delegation call and the final report. A failure in `prepare_code_review` is a tool error inside the child, and the child reports it instead of inventing a review. `prepare_code_review` can also be called directly by a model without the command.

The generated `index.md` lists every file with its patch and full text path, and records anything omitted because of limits. The agent can fetch a missing file read-only with `gh api` when it needs one.

## Review behavior

The bundled `dsh-code-review` skill defines the procedure: read the change, use the complete file for context, look for concrete defects, then try to falsify every candidate finding against the code before reporting it. Findings carry a severity and an exact `path:line`; pure style preferences are not reported.

The review is read-only by instruction: the prompt forbids modifying repository files, committing, and posting to GitHub. It does not change the session's permission preset, so choose a read-only preset when you want enforcement.

A project skill named `dsh-code-review` under `.dsh/skills` or `.agents/skills` takes precedence over the bundled methodology, so a repository can tune the rubric without changing the plugin.

## Configuration

The five fields people change most are editable in the Web UI: open **Plugins** and select **Code review**. The settings card is on the package page; the same form is also on the `code-review` row. It saves through the Harness settings service, so a change is validated by the Host and applies to the next review without restarting the plugin. An overridden field carries a badge and can be reset to the deployed default. The same five fields are accepted in the row's `config` in `cordis.patch.yml`:

| Field | Default | Meaning |
|---|---|---|
| `language` | `auto` | Report language: `auto`, `zh`, or `en` |
| `maxFindings` | `15` | Findings the reviewer may report |
| `maxFiles` | `200` | Maximum changed files fetched into the context |
| `maxPatchBytes` | `262144` | Per-file patch cap; a longer patch is truncated with a marker |
| `retentionDays` | `7` | Old review context directories are pruned after this many days |

The remaining fields are deployment limits and stay in `cordis.patch.yml`; they are validated at activation and changing one reloads the plugin:

| Field | Default | Meaning |
|---|---|---|
| `ghCommand` | `gh` | Executable used for GitHub reads |
| `maxFileBytes` | `131072` | Per-file complete-text cap; larger files keep only their patch |
| `maxTotalFileBytes` | `8388608` | Total complete-text budget across the context |
| `requestTimeoutMs` | `30000` | Deadline for one `gh` invocation |
| `concurrency` | `4` | Concurrent file fetches |

## Limits and privacy

- Pull request metadata, patches, and complete file text are sent to the session's model as review input. Do not review private pull requests in a session whose provider may not receive that content.
- Only the first `maxFiles` changed files are fetched; a larger pull request is truncated and the omission is recorded in `index.md`.
- Binary files, generated files, lockfiles, and minified assets are skipped for complete text.
- The plugin never checks out the pull request and never writes to the reviewed repository. Review context lives under the session directory and is ignored by Git through a local `.gitignore`.
- Reviewing a pull request does not run its tests.

## Development

The Host plugin, tests, and scripts are TypeScript and run directly under Node's type stripping. Building and testing are separate steps: run `npm run build` first, then `npm test` consumes the resulting `lib/` and never rebuilds it. `tsdown` produces both halves of the package: the Host bundle `lib/index.js` (with `lib/index.d.ts`) and the browser bundle `lib/client.js`, which wraps the hand-written `src/client/index.js` module in the loader factory the Harness serves. `lib/` is git-ignored build output: a checkout generates it with `npm run build`, while the `.deb` is built from source and ships the built `lib/`. `npm test` assumes `lib/` already exists.

```sh
npm install
npm run build        # tsdown -> lib/ (run this before tests or packaging)
npm test             # node --test against the built lib/ (does not build)
npm run typecheck    # tsc --noEmit
npm run dry-run -- https://github.com/owner/repo/pull/123
make test            # build, then typecheck and test
make deb             # build, test, package and verify the Debian package
make verify          # re-run the package checks
```

`dry-run` builds the review context with a local `gh` runner and prints the prompt instead of starting an agent turn. It is the fastest way to check selector parsing, GitHub access, and context budgets before installing.

### Types

The DSH Host API is imported **type-only** from exact-version devDependencies, not hand-written, with one runtime exception: [`@deepseek-ai/schemastery`](https://www.npmjs.com/package/@deepseek-ai/schemastery) builds the row's `Config` schema at runtime. The `.deb` stages it, with its `cosmokit` dependency, inside the installed package root; an npm install resolves it as a normal dependency. Every other DSH package is build-only:

- `@deepseek-ai/cordis` `4.1.0`
- `@deepseek-ai/schemastery` `3.19.0` (runtime)
- `@deepseek-ai/dsh-agent`, `-commands`, `-llm`, `-settings`, `-skill`, `-subprocess`, `-tools`, `-working-directory` `0.2.2-rc.3`

The versions are pinned because npm's `latest` tag for the DSH packages is stale (`0.0.1-rc.1`); installing without an explicit version would fetch an incompatible API. Apart from `schemastery`, the compiled `lib/` has no `@deepseek-ai/*` import — verify with:

```sh
! grep -rE "from ['\"]@deepseek-ai|import ['\"]@deepseek-ai|require\(['\"]@deepseek-ai" lib --include=*.js \
  | grep -q -v '@deepseek-ai/schemastery'
```

When upgrading the Harness, update these devDependencies (and the `schemastery` runtime dependency) to the installed versions and rebuild. Domain types (`Settings`, `ReviewMeta`, `ContextEntry`, and so on) remain local because they describe this plugin's own files, not a DSH contract.

### Layout

| Path | Role |
|---|---|
| `src/index.ts` | Bundle entry: `apply()`, `inject`, `Config`, command/skill/tool registration |
| `src/client/index.js` | Browser half: the settings card on the plugin and row pages (bundled to `lib/client.js`) |
| `src/command.ts` | `/code-review` handler: validate and submit the delegation turn immediately |
| `src/tool.ts` | `prepare_code_review`: fetch and materialize the review context for the child |
| `src/context.ts` | Review context builder |
| `src/pull-request.ts`, `src/gh.ts` | GitHub reads through `ctx.subprocess` |
| `src/skill.ts` | Embedded `dsh-code-review` methodology |
| `src/types.ts` | Domain value types and type-only re-exports of the DSH Host API |
| `tests/` | `node:test` suites, run from source under Node's type stripping |
| `tsdown.config.ts` | Build faces: Host ESM bundle, browser CJS loader bundle |
| `lib/` | Build output (git-ignored): Host entry/declarations and the client bundle |
| `release.conf`, `Makefile` | Debian package identity and the `make deb` pipeline |
| `scripts/` | Build, staging, packaging, and verification scripts |
| `packaging/` | Debian `control`/`postinst` templates and package docs |
| `.github/workflows/` | `ci.yml` (PR tests) and `build-deb.yml` (tag release) |
